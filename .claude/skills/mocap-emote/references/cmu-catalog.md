## 검색 방법

- 브라우저로 `https://mocap.cs.cmu.edu/search.php?subjectnumber=<N>` 접속 → 해당 subject의
  trial 목록(설명 텍스트) 확인. 설명 없이 숫자만 있는 subject도 있음 — 그럴 땐 이름으로
  판단(예: "Jump", "salsa dance").
- 전체 subject 목록은 `search.php?subjectnumber=55` 같은 아무 페이지나 접속해도 좌측에
  "View All: Subjects" 링크로 전체 목록이 뜬다(카테고리별로 훑기 좋음).
- 파일 URL 패턴: `https://mocap.cs.cmu.edu/subjects/<N>/<N>.asf` (스켈레톤, subject당 1개),
  `https://mocap.cs.cmu.edu/subjects/<N>/<N>_<trial2자리>.amc` (모션, trial마다).
  링크가 페이지 렌더링에 안 뜨면(프레임 구조) `javascript_tool`로
  `document.querySelectorAll('a')`의 href를 훑으면 나온다.

## 누워서 도는 동작(바닥 브레이크댄스) — 진짜 데이터로 하는 법 (2026-07-27, 세 번 실패 후 확정)

**★최종 결론부터: root의 실제 회전을 그대로 따라가지 말 것.** baseline-relative
decompose(아래 실패2 다음 시도)까지도 "여기저기 360도 날아다닌다"는 피드백을 받고
실패했다 — 실제 윈드밀은 어깨/등이 바닥에 거의 고정된 채 **다리만** 크게 원을 그리는
동작인데, root(우리 리그 기준 골반 근처)로 몸통 전체를 실제 캡처값만큼 회전시키면
골반의 실제 이동거리가 상체 전체에 그대로 곱해져 나사가 풀린 듯 크게 빙빙 도는 것처럼
보인다. **성공한 최종 구조**: root(+허리·가슴·머리·팔)는 **엎드린 자세로 고정**(회전
안 함, 위치도 고정) 하고, **다리(허벅지+무릎)만** mocap의 실제 로컬 회전을 그대로
써서 진짜 원을 그리며 스윙하게 둔다 — 상체는 안정된 피벗, 하체만 도는 진짜 윈드밀의
시각 문법을 그대로 재현한 것. 아래는 그 과정에서 실패한 두 시도 기록(교훈 보존용).

"우리 리그는 서있는 자세만 가능"이라는 건 틀렸다 — 다리를 실제 mocap으로 크게 돌리면
누워서 도는 것도 진짜처럼 나온다(디스가이즈라 히트박스와 무관). **단, root(몸통 전체)를
어떻게 다루느냐가 관건이고, 아래 세 번 실패한 뒤에야 답을 찾았다:**

**★실패1 — 손으로 눕기만 시킴**: root X회전을 88도로 고정+홀드하고 다리만 mocap을 썼더니
"그냥 뒤로 누웠다 일어나기"로 보임(유저: "누가 뒤로 누워서 하냐"). 정적 홀드는 죽은
동작으로 읽힌다.

**★실패2 — 눕기+합성 스핀(Y축 계속 증가)**: 실제 회전 대신 내가 지어낸 스핀을 얹었더니
여전히 부자연스러움(유저: "추론 좀 그만하고 제대로 된거 찾아").

**★실패3 — root의 실제 회전을 baseline 대비 상대값으로 그대로 재생**: 짐벌락 문제를
제대로 풀어서(아래 기법 자체는 유효함) root가 실제 캡처값만큼 정직하게 돌게 했는데도
"여기저기 360도 날아다닌다", "앞으로 눞지 않는다"는 피드백. **원인**: 실제 윈드밀은
어깨/등이 바닥에 거의 고정된 채 **다리만** 원을 그리는 동작인데, root(우리 리그 기준
골반 근처)를 몸통 전체의 피벗으로 놓고 골반의 실제 3D 회전을 그대로 따라가면, 골반의
회전이 위로 연결된 상체 전체(허리→가슴→머리)에도 그대로 곱해져서 상체까지 크게
휩쓸리며 도는 것처럼 보인다 — 실제 사람은 그렇게 안 움직인다(상체는 지면에 거의
고정, 하체만 도는 게 윈드밀의 핵심). 짐벌락 회피용 기법(baseline 상대 decompose)은
남겨두되, **몸통 전체 회전에 그대로 갖다 쓰면 안 된다는 게 이번 교훈**:
```python
baseline_rot = euler_xyz(*frames[0]["root"][3:6])
baseline_inv = mat_transpose(baseline_rot)
R_rel = mat_mul(baseline_inv, euler_xyz(*frame["root"][3:6]))
rx, ry, rz = decompose_xyz(R_rel)   # 짐벌락은 피하지만 root 전체에 곧이곧대로 쓰면 안 됨
```

**★★성공한 구조 — root는 엎드린 채 고정, 다리만 실제 회전**:
- `player_root` + 허리/가슴/머리/팔: **회전·위치 전부 고정**(rx=-88 한 번만 줘서 앞으로
  엎드린 자세, 그 뒤로 안 움직임). 팔은 "그럴듯한 브레이스 포즈"로 약간만 고정 각도.
- 다리(prl/pll 허벅지 + prfl/plfl 무릎)만 **mocap 실제 local_rot을(평균중심화 없이,
  smooth+clamp만) 그대로** 사용 — root가 고정이라 이 회전이 곧 다리의 진짜 궤적으로
  화면에 보인다. 이게 "상체는 안정된 피벗, 하체만 크게 도는" 진짜 윈드밀의 시각 문법.
- 바닥 구간은 ty(root 높이)가 클립 전체에서 가장 낮게 유지되는 슬라이딩 윈도우로 찾는다
  (Helicopter는 프레임 640~960 근방, 서있을 때 ty≈16~17에서 바닥 구간엔 3.8까지 떨어짐).

**교훈 일반화**: 바닥 동작처럼 "한 부위는 고정, 다른 부위만 크게 도는" 실제 동작을
리타게팅할 때는 **root를 실제 데이터로 따라가게 하지 말고, 어느 관절이 진짜 피벗인지
먼저 판단해서 그 관절 기준으로 나머지를 상대운동시킬 것.** root=몸통 전체라는 가정이
항상 맞는 게 아니다.

**함정들**:
- retarget.py 기본 `bake_into()`는 root에 rotation 채널을 아예 안 만든다(모캡 root는
  원래 position만 씀) — 조건부로 "기존 리스트 있으면 추가"하면 **빈 리스트라 아무 일도
  안 일어남**. root rotation은 항상 처음부터 새로 만들 것.
- **subject 85는 120fps**(대부분 60fps인 다른 subject와 다름) — dt 계산에서 프레임레이트
  꼭 확인. 이 케이스는 범용 retarget.py CLI(60fps 고정)로 안 돌리고 전용 스크립트로
  처리했다(TODO: `--fps` 옵션 추가하면 CLI로 통합 가능).
- 서서 추는 구간과 이어붙이지 말고(유저: "서서 댄스 없어도됨") **바닥 구간 하나만으로
  루프 전체를 구성**하는 게 더 깔끔했다 — 굳이 서있는 인트로를 붙이지 말 것.

## 소스 선택 체크리스트

1. Trial 설명에 "flip", "handstand", "cartwheel", "fall", "stumble" 있으면 제외
   (우리 리그는 서있는 자세만 표현 가능 — 바닥/역전 자세 없음).
2. `retarget.py scan`으로 에너지 점수부터 확인 — 너무 낮으면(<100 정도) 그 클립 자체가
   전반적으로 밋밋할 수 있음(다른 trial 시도).
3. **길이(window-sec) 4~5초 이상 권장** — 2~3초로 짧게 자르면 루프가 금방 반복돼
   "싸구려" 느낌이 난다는 피드백을 실제로 받음. 소스 클립 길이의 60~70% 이내로.
