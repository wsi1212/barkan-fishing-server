## 조치 완료 (이번 감사에서 즉시 수정, 코드 컴파일 확인·커밋 완료)

### 1. [🔴→✅] 히든 낚싯대 8종 획득경로 버그
- **증상**: `WetTreasureChestManager.randomLockedRecipe()`가 낚싯대 레시피를 골라낼 때
  `"낚시".equals(rec.category)`로 비교했는데, 실제 라이브 `recipes.json`의 낚싯대 레시피는
  전부 `category: "낚싯대"`다. 이 비교가 단 한 번도 참이 될 수 없어 preferred/fallback 풀 모두
  낚싯대 레시피를 담지 못했고, 그 결과 젖은 보물상자의 "레시피 보상"(개봉 시 5% 확률)에서
  **낚싯대는 절대 나올 수 없었다**(대신 돈으로 대체 지급됨).
- **왜 이게 심각한가**: 코드는 명시적으로 `parts.getOrigin("낚싯대", rod).startsWith("히든")`인
  레시피를 `preferred`(우선)로 분류하는 로직까지 갖춰뒀다 — 즉 **"히든 낚싯대를 보물상자로 우선
  지급한다"는 의도된 설계가 이미 있었는데, 카테고리명이 `"낚시"→"낚싯대"`로 바뀌는 리팩터링 과정에서
  이 한 줄만 안 고쳐진 것**으로 보인다. balance.md §7(2026-06-10)이 "S=히든 전설 2종만" 재설계한
  시점과 맞물려 있어, 그 리밸런스 때 카테고리명이 바뀌었을 가능성이 높다.
- **영향 범위**: parts.json 84종 중 "출처"가 히든인 8종 **전부** — A급 6종(여명·신기루·행상인·수호자·
  사막군주·대상인) + balance.md가 "S=히든 전설 2종"이라고 명시한 대표 엔드게임 낚싯대 2종(바르칸·천공)
  까지 전량. 이무기 보스가 주는 "용비늘"(바르칸·천공 레시피 재료)도 이 버그 때문에 사실상 무용지물이었다.
- **수정**: `"낚시"` → `"낚싯대"` 한 글자 교체. (`blockship-plugin` 커밋 `92c8b7d`)
- **수정 후 기대 획득 빈도**: 보물상자 자체 등장률 1.2~3.0%/캐스트(행운별) × 레시피보상 5% ≈
  0.06~0.15%/캐스트. 150캐스트/h 가정 시 **평균 4.4~11시간마다 1개**(currently-locked 히든 레시피
  중 균등 랜덤) — 8종을 다 모으는 데 대략 수십 시간 걸리는, 엔드게임 "가끔 터지는 잭팟" 페이싱으로
  적절해 보인다.
- **부수 조치**: balance.md §8.1의 히든 낚싯대 행운 수치가 구문서(A=7~9,S=10~11)로 드리프트돼 있어
  실측값(A=14~18,S=20~22)으로 정정(⚪ 드리프트, 코드가 맞고 문서가 낡음).
- **미해결로 남긴 것**: `quests.json`의 `히든_수호자`/`히든_사막군주`/`히든_대상인` 3개 퀘스트 항목은
  `보상레시피` 필드가 있지만, **어떤 NPC의 `quests` 배열에도 등록돼 있지 않아 플레이어가 수락할 방법이
  없다**(QuestCatalogGui도 "히든" 카테고리 탭이 없음). 즉 이 3개는 보물상자 경로와 별개로 존재하는
  **미완성 보조 경로**로 보인다. 보물상자 경로가 이미 8종 전체를 커버하므로 기능상 급하지 않지만,
  NPC 연결이 원래 의도였다면 추가 작업 필요 — 사용자 판단 필요(조치권고 참조).

### 2. [🟡→✅] 송금 수수료 이중과금
- **증상**: `TransferCommand`가 안내 문구·명령어 설명엔 "수수료 10%"라고 표시하지만 실제로는
  송신자에게 `amount + fee`(110%)를 차감하고 수신자에게는 `amount - fee`(90%)만 지급 —
  **실제 소멸분은 20%**였다.
- **수정**: `deduct = amount`로 정정(송신자는 amount만 지불, 그 중 10%가 수수료로 소멸, 수신자는
  90% 수령) — 안내 문구와 실제 효과 일치. (커밋 `92c8b7d`)
- **참고**: 악용/복제 리스크는 없었다(오히려 서버에 유리한 방향의 버그) — 유저 신뢰·안내 정확성
  문제였다.

### 3. [🔴→✅] 드릴 티어 배치 오류 (사용자 지적으로 발견)
- **증상**: `DrillManager.java`는 원래 "1단계=흑정석(mine 월드)", "2단계=자수정(레드_로드 지역)"으로만
  코딩돼 있었다. 이번 감사 초안에서 "T3(정예 드릴)는 T1/T2와 완전히 같은 광물만 캐고 티어 전용
  자원이 없다"고 판정했는데, **실제로는 두 번째 광산이 레드_로드가 아니라 regions.json의 "광산"
  지역**(아이콘 `RAW_IRON_BLOCK` — 사막마을 소속)이었다. 이 지역은 이미 실측(`mc_find_blocks_in_region`)
  으로 `raw_iron_block` 8개가 실제로 배치돼 있는 것까지 확인됐다 — 즉 **"광산"이 진짜 두 번째
  광산이고, 자수정을 2단계로 넣은 것 자체가 처음부터 오배치**였다.
- **수정**: `DrillManager.java`에 "광산" 지역을 채굴 존으로 신규 등록(`SECOND_MINE` 상수)하고,
  철원석블럭/갈색 유리/갈색 유리판 기반 "철광석" 광맥 3종을 Tier2로 신설, 기존 자수정 4종은
  Tier3(레드_로드 유지)로 재배치했다. 밸런스 수치(breakTicks·재생초·수량)는 기존 자수정 항목
  값을 그대로 재사용해 새 값을 임의로 지어내지 않았다. `materials.json`에 "철광석"(mcItem
  `raw_iron`) 신규 등록. (`blockship-plugin` 커밋 `d37aca6`, JSON 백업
  `materials.json.bak-20260725-drilltier-before`)
- **✅ 밀도 확인 완료(사용자 확인)**: 필자가 `mc_find_blocks_in_region`로 광산 지역을 스캔했을 때
  8개(RAW_IRON_BLOCK만)밖에 못 찾아 "노드가 너무 적다"고 오판했으나, **사용자가 직접 확인 —
  실제로는 prod 광산 월드에 충분히 많다.** 이 도구가 레드_로드(points3d 셰이프)에서도 AABB가
  1x1x1로 깨지는 걸 이미 한 번 겪었듯, 폴리곤 지역에서도 스캔 누락이 있었던 것으로 보인다
  (원인 미상 — 도구 한계로 결론, 재조사하지 않음). **밀도 관련 조치 불필요**.
- **영향**: 항목4의 "T3가 티어 전용 자원이 없다"는 결론은 **철회** — 정정 후엔 T2가 철광석,
  T3가 자수정을 각각 독점 해금하므로 정상적인 티어드 콘텐츠 구조다. 티어 배치 버그 수정으로 완결.

  원/h 0으로 처리해서 생기는 **측정 아티팩트일 가능성**과 **진짜 설계상 약한 아이템일 가능성**을

### 항목4 — 행동별 최종값 수익 밸런스 (낚시/드릴/광질/농사)
- 기존 mining 감사가 드릴을 이미 다뤘음(A절) — 이번엔 그때 보류했던 실제 계산을 완료.
- **드릴 처리량은 노드 재생시간(180~480초)이 지배** — 드릴 배속을 1.0→3.5배로 올려도 "노드 하나
  반복" 시나리오에선 처리량이 겨우 +12%만 증가(268.5원/h→301.9원/h). 밀집 노드를 자유로이 옮겨다닐
  수 있으면 배속에 정비례(최대 113,770원/h, 낚시의 3.5배)까지 오른다 — **실제 값은 광맥 밀도(서버
  빌드 데이터, 코드에 없음)에 전적으로 좌우**돼 확정 불가.
- ⚠️ **정정(조치 완료 3 참조)**: 초안은 "T3(정예 드릴)가 T1/T2와 완전히 동일한 광물만 캐고 티어
  전용 자원이 없다"고 판정했으나, 이는 두 번째 광산을 레드_로드로 잘못 짚은 데서 나온 오류였다.
  실제로는 T2가 "광산" 지역의 철광석을, T3가 레드_로드의 자수정을 각각 독점 해금하도록 이미
  코드에 있었어야 했고(2026-07-25 재배치 완료), 정상적인 티어 구조다. 다만 원래 보고했던
  "T2→T3 업그레이드비 32,395원 대비 floor 시나리오 회수 5.3년" 수치는 **당시 T3=자수정 기준
  계산**이라 재배치 후에도 티어3 자체의 손익분기 규모감은 참고할 수 있지만(3단계 광물이 여전히
  자수정이므로), 정확한 재계산은 "광산" 지역의 얇은/보통 단계 광맥이 물리적으로 배치된 뒤 실측
  기반으로 다시 해야 한다.
- 섬광산(islandmine)은 기존 감사에서 이미 "즉시재생+호퍼캡+상점 인챈트 상한"으로 실질 안전 확인됨
  (~32,400원/h로 낚시 앵커와 거의 동일 — 처음부터 "즉시재생"이라 floor=ceiling).
- 농사는 원/h 개념이 안 맞아(슬롯임대료 모델) 직접 비교는 어려우나 기존 farming 감사(수박 이상치
  1건 외 양호)로 대체.
- **사용자가 제시한 이상적 순서**(초반 낚시>드릴>광질>농사, 최종 농사≥낚시≫광질≥드릴)와 대조 시:
  드릴이 밀도 의존이라 낚시>드릴 순서가 실측 없이는 검증 불가하다는 게 이번 감사의 핵심 결론.
  드릴 T3 자체의 "속도만 팔고 티어 전용 자원이 없다"는 설계는 밀도와 무관하게 개선 여지가 있다.

### 항목5 — 마을별 퀘스트 난이도 분포
- 정식 4개 마을(본섬38·사막43·상단21·왕도24) + 튜토(23, Lv1 고정) + 일일/주간(비마을).
- **왕도만 극악난이도 캡스톤이 없다** — 다른 3개 마을은 전부 Lv60 히든 낚싯대 시험(S등급 낚시)이라는
  실행난이도 있는 캡스톤을 갖는데, 왕도의 최고 퀘스트(왕도15, Lv40)는 목표가 대화(`visit`)뿐이라
  레벨 게이트만 높고 실행 난이도는 없다. 사냥 난이도 상한도 A등급(왕도09)에 그쳐 다른 마을 중반부
  보다도 낮다.
- **반대 방향 문제**: 본섬·사막마을의 Lv8~12 사이드퀘스트 3개(본사이드_마리02·세르간04, 사사이드_
  사피르03)가 **Lv60 히든 캡스톤과 동일한 실행난이도**(S등급 낚시 1마리)를 요구한다. GradeRoller
  확인 결과 S등급은 전 레벨 공통 기본확률 0.21%(피티 누적으로 완화)라 저레벨 신규 유저에게는 예상
  밖의 RNG 벽이 될 수 있다 — 다만 피티가 레벨게이트 이전부터도 누적된다는 기존 확립 원칙([[feedback_no_arbitrary_stat_caps]]
  관련 세션에서 확인된 PRD 설계) 감안 시 체감 난이도는 실측 없이는 확정 어려움.
- 마을 간 퀘스트 개수 편차: 사막(43) vs 상단(21) 약 2배 — 극단적이진 않지만 뚜렷.

### 항목6 — 기타 미감사 시스템 (마켓/랭킹/여관/송금/길드/스킬트리/카지노)
- **마켓**: 수수료 10% 정상 소멸(재생성 안 됨), 자기거래 차단 확인. **정상**.
- **랭킹**: money 직접 지급 없음, 실제 보상(섬 제출 top3)은 별도 화폐(추천코인)라 인플레 무관. **정상**.
- **여관/사망**: 사망 페널티 5,000원 고정 + 인벤/경험치 100% 보존 + 거점워프 완전무료. 억제력이
  다른 소액 싱크(도핑상점 5,000, 확성기 5,000)와 동일 수준이라 **상대적 무게감 재검토 여지**(수치
  자체가 틀린 건 아니라 "이 정도로 충분한가"의 설계 판단).
- **송금**: 위 "조치 완료 2"로 수정됨.
- **길드**: 별도 뱅크 없음(작물/업그레이드/제출랭킹 코인뿐) — 해당사항 없음.
- **스킬트리**: 포인트=레벨업 전용, 초기화 P당 5,000원 순수 싱크. **정상**.
- **카지노**: 슬롯 RTP 93.92%(하우스엣지 6.08%, 코드에 assert까지 있음), 룰렛 유럽식 표준(~2.7%),
  홀덤 칩스택 기반(복제 불가). **정상**.
- **아이스박스/제작해금**: 9단계 누적 109만원, 재료 최초 획득 시 자동해금(무료). **정상**.

## 조치 권고 (우선순위 순, 사용자 결정 필요)

1. **[정보 확인 권고]** 히든 낚싯대 퀘스트 3개(`히든_수호자`/`히든_사막군주`/`히든_대상인`)를 NPC에

   뿐). 원래 퀘스트 경로도 살릴지, 아니면 죽은 데이터로 정리(삭제)할지 결정 필요.

3. **[설계 판단]** 왕도 캡스톤 부재 — 다른 3마을처럼 Lv60 실행난이도 있는 퀘스트 신설 여지(예:
   왕도 스토리와 자연스러운 결합점 필요, 6장 스토리 작성과 함께 갈 수도 있음).

   일일/주간 Lv20 이후 — 만렙 100 대비 후반부 퀘스트 콘텐츠가 구조적으로 빔. 밸런스 조정이 아니라
   콘텐츠 제작이 필요한 영역.
6. **[측정 개선]** stat-values.md가 "난이도" 스탯을 원/h 0으로 처리해 예민한 찌/초정밀 찌가 실제보다
   나빠 보일 수 있음 — 난이도 스탯의 실질 가치(미니게임 실패율 감소→시간당 유효 캐스트 증가분)를
   추정해 반영하면 항목1의 B등급 이상치 판정이 바뀔 수 있음.

   메커니즘이 다른데 가성비 자체는 문제없어 우선순위 낮음.
