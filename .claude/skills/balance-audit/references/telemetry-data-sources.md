# 낚시 텔레메트리 — 크리 가치 측정 규약

크리확률은 캐치 1회에 한 번 굴리는 확률이 아니다. `MinigameManager`가 **성공 존의 각 칸마다**
독립적으로 금칸을 만들고, 플레이어가 보이는 금칸을 조준해 클릭해야 크리가 된다. 따라서 부품의
`크리확률:48`을 "크리 48%"로, `크리배율:12`를 "상시 판매 +72%"로 읽으면 안 된다.

## 권위 소스와 읽기 전용 범위

★**맥(dev)의 `plugins/BlockShip/telemetry/` 를 읽으면 안 된다.** 그건 부분 미러다. 2026-09-14 실측으로
dev `events-2026-09.db` 는 3 MB·4,514캐치·16명·09-05에서 끊겨 있었고, 같은 시각 prod 는 698 MB·80,208캐치·
239명이었다. 스키마도 파일명도 같아서 **조용히 17배 작은 표본으로 다른 결론**이 나온다(실제로 09-13 감사가
"현행 체계 표본 0건 — 미측정"으로 끝났다). 텔레메트리 근거는 **항상 prod 박스에서 읽는다.**


| 대상 | 위치 | 쓰임 |
|---|---|---|
| 결과 원본 | `plugins/BlockShip/telemetry/events-YYYY-MM.db`, 테이블 `ev` | `fish.result`의 실제 크리 결과·명목 크확·크리배율·가격·XP |

| 로드아웃 | 같은 DB의 `loadout` | `fish.result.ctx.lo` 해시의 장비 이름 확인. 이름/UUID를 보고서에 쓰지 않는다. |
| 메커니즘 | `blockship-plugin/.../fishing/MinigameManager.java`, `FishingListener.java` | 필드 의미와 보상공식 검증 |

SQLite는 `mode=ro`로만 연다. 원본 DB·`stats.db`·플레이어 데이터는 수정하지 않는다. 리포트와
스냅샷에는 이름·UUID·개별 타임스탬프를 넣지 않고, 최소 3명/100결과 미만의 장비 구간은
익명성·일반화 모두를 위해 **표본 부족**으로 표기한다.

## 필수 분해

크리의 수입 가치는 다음 네 층을 분리해 기록한다.

1. **금칸 존재율** — 명목 칸 확률 `p`, 해당 판 존폭 `w`에서 기계상 `1-(1-p)^w`. 존폭은 등급·크기·난이도로 달라진다.
2. **조준 전환율** — 금칸이 있었을 때 실제 금칸을 클릭한 비율.
3. **실현 크리율** — 결과 크리 / 성공·크리 결과. 이는 1·2층과 실패·다중라운드 효과가 합쳐진 관측값이다.
4. **보상 프리미엄** — 크리배율 `d`일 때 코드상 판매가 `+6d%`, 경험치 `+10d%`가 크리 발생시에만 적용된다. 기본 `d=1`도 포함한 최종 `FishingBonuses.critDamage`를 쓴다.

현재 과거 `fish.result`에는 3·4층과 명목 `p`는 있으나 존폭·금칸 존재가 없다. `fish.macro`는 1·2층의
요약을 남기지만 loadout/명목 `p`/존폭과 결합되지 않는다. 그러므로 과거 데이터로 "실제 크리율"은
측정해도, 특정 부품 1포인트가 금칸 생성과 조준에 준 인과효과를 단정해서는 안 된다.

## 판매보너스와 분리한 수익 가치

현재 크리의 직접 판매가 체계는 **2026-09-13 KST부터**다. 그 이전 `fish.result`의 가격·`critd`는
과거 보상공식에서 나온 값이므로 현행 크리 수익과 합산하지 않는다. 과거 데이터는 명목 크확에 대한
**결과 크리율 반응**을 보는 보조 자료로만 쓴다.

현행 체계 수익은 `판매보너스 등가치(SB-eq)`로 기록한다.

```text
SB-eq = Σ[ floor(basePrice × (1 + 0.06 × d)) - basePrice ] / Σ basePrice
```

- `basePrice` = 등급 기본가 × 품질점수 배율. **크리·판매보너스·신선도 적용 전** 가격이다.
- `d` = 실제 크리 결과에 찍힌 최종 크리배율(기본 1 포함).
- 따라서 SB-eq `+x%`는 "같은 기본가에 판매보너스 +x%"와 동등한 순수 크리 수익이다. 다른 판매보너스
  스탯이 높은 유저가 있어도 이 값을 부풀릴 수 없다.
- 크리배율 1점의 빌드 내 한계가치는 `실제 결과 크리율 × 6%p SB-eq`다.
- 명목 크확 1점의 한계가치는 `6 × d × (결과크리율의 변화)`이며 비선형이다. `크확 n% = SB-eq n%`
  같은 환산은 금지한다.

`crit_telemetry.py`의 기본 `--revenue-since 2026-09-13`은 이 경계를 강제한다. 이후 표본이 100캐치·3명
미만이면 SB-eq는 **수익 미측정**으로 남긴다.

## 실행과 판정

```bash
# ① 상수만 — prod 박스에서 집계해 JSON 만 받는다 (DB 를 내려받지 않는다)
python3 .claude/skills/balance-audit/scripts/crit_telemetry.py --remote

# ② 전체 표 (명목별 실현율·SB-eq·조준전환) — 로컬 캐시 기준
python3 .claude/skills/balance-audit/scripts/crit_telemetry.py --out /tmp/crit.json

# ③ 특정 바늘의 실사용 표본만
python3 .claude/skills/balance-audit/scripts/crit_telemetry.py --hook '사구 바늘'
```

**맥의 `plugins/BlockShip/telemetry/` 를 가리키지 말 것** — 부분 미러다(위 경고 참조).

받는 건 더 이상 유지되지 않으므로, 상수 갱신은 `--remote` 를 쓴다. 내부적으로 이 스크립트를
박스에 올려 `~/crit-audit/run/` 에서 돌린다 — 얕은 경로면 기본 인자의 `Path.cwd().parents[1]`

- `실현 크리율`: 각 명목 크확별 결과 수, 고유 플레이어 수, Wilson 95% 구간을 반드시 함께 본다.
- `측정 가능`: 최소 100 결과와 3명. 30 결과/2명은 **참고만**, 그 미만은 **표본 부족**이다.
- `fish.macro`의 `gold_conv`는 `gold_n`으로 가중 평균한다. 스냅샷 수 평균을 내면 안 된다.
- 부품 단위 결론은 `--hook`으로 `loadout`을 결합해 먼저 해당 장비의 표본을 확인한다. 장비 표본이
  없거나 기준 미달이면 같은 크확 수치의 다른 장비·다른 유저 데이터로 대체하지 않는다. `fish.macro`는
  로드아웃을 갖지 않으므로 바늘 필터에서는 사용하지 않는다.
- 현재 `critd`는 크리 결과에만 기록되어 같은 빌드의 비크리 대조군을 만들 수 없다. 보상 프리미엄은
  평균 가격 비교가 아니라 코드 공식(판매 `+6d%`, XP `+10d%`)을 우선한다.
- `sale_value_excluding_sell_bonus`는 현행 체계 이후에만 읽는다. 여기의 `equivalent_sell_bonus_pct`가
  크리 **묶음**(발생률×배율)의 판매 수익 가치다. 현행 표본이 없으면 0이 아니라 **미측정**이다.
- 표본이 부족하면 합성 20%/배율4 같은 임의 기본값으로 바꾸지 않는다. "미판정"으로 두고, 메커니즘 기반 반사실 시뮬레이션을 별도 가정으로 표기한다.

### 명목 → 실현 환산은 한 곳에서만

`realised_from_nominal()` / `REALISED_FIT` 가 단일 권위다. `크리확률/100` 으로 읽는 코드를 새로
만들지 말 것 — `gold_curve.py`·`gold_curve2.py` 가 그렇게 돌다가 저·중구간 크리 수입을 2배 이상
과소평가했다(2026-09-14 수정). 곡선은 손으로 고치지 말고 `fit_realised_curve()` 로 다시 뽑는다.

### 금액가중을 쓴다

`SB-eq = r × d × 6%` 는 **금액가중**일 때만 성립한다. 크리배율이 높은 빌드가 비싼 물고기를 잡아
개수평균 배율(8.21)과 금액가중 배율(9.75)이 다르고, 개수가중으로 재면 15.86% 로 나와 실측
19.08% 를 17% 과소평가한다. `crit_constants()` 가 둘 다 낸다.

`gold_available`, `gold_hit`, `crit_chance`, `crit_damage`, `round_count`를 함께 기록하는 계측 변경을
