# steve.bbmodel 리그 규약 (mocap 리타게팅이 준수해야 할 것들)

경로: `plugins/BetterModel/players/steve.bbmodel` (dev는 이 파일이 곧 서버 파일,
prod는 scp로 미러). 13본 + shadow/tag_name/cape 등 비애니 본.

## 본 계층

```
player_root (전체 이동/회전 핸들 — 점프·바운스·체중이동·스핀은 여기)
├─ phip_hip (애니 안 씀, 항상 무회전)
├─ pw_waist → pc_chest → h_ph_head
├─ pra_right_arm → prfa_right_forearm (→ pri_right_item, 손끝)
├─ pla_left_arm → plfa_left_forearm (→ pli_left_item)
├─ prl_right_leg → prfl_right_foreleg
└─ pll_left_leg → plfl_left_foreleg
```

레그(prl/pll)는 phip_hip이 아니라 **player_root의 직계 자식**이다(주의 — 골반 자체는
애니 안 됨).

## 축 부호 규약

- **오른팔(pra) +Z = 바깥쪽, 왼팔(pla) −Z = 바깥쪽** (몸 가로지르는 방향 = 반대 부호,
  나치경례처럼 보이는 큰 각도 전방 상향 단일팔 자세는 금지 — 유저 강피드백으로 확립).
- **팔 X = 전후**(양팔 동일 부호, 좌우 안 갈림 — 앞으로 나란히는 둘 다 +X).
- **다리 X = 전후 킥**, Z는 약한 turnout(±10 내외)에만 씀.
- **전완(팔꿈치) 회전은 X만** — Y/Z 안 씀(비틀림은 어색해 보임).
- **머리는 X=끄덕, Y=도리도리**. Z(갸웃)는 지금까지 안 씀.

## 팔꿈치/무릎 관절 — 2026-07-27부로 허용됨(과거엔 금지였음)

과거엔 "전완/정강이는 회전 금지, 상완/허벅지만" 이라는 룰이 있었다(이유: 굽히면
"팔꿈치서 갈라져 두 조각으로 보임"). **재검증 결과 이건 z-fighting이었다** — 원인은
관절 자체가 아니라 인접 면의 좌표가 완전히 일치해서 생기는 렌더 깜빡임/이격이었고,
`ZFIGHT` 딕셔너리처럼 **x/y/z 중 하나라도 확실히 다르게** 오프셋을 주면 해결된다(z만
다르면 부족한 경우가 있었음 — x,y도 조금씩 어긋나게 줄 것, `retarget.py`의 ZFIGHT
값 참고). 그래서 이제 팔꿈치·무릎 실제 굽힘을 자유롭게 써도 된다 — 인게임에서
유저가 직접 확인하고 승인함("괜찮은데??").

## ★ 몸 관통 + 잔떨림 함정 (2026-07-27, 실제 겪은 버그 — retarget.py에 수정 반영됨)

exaggeration 배율(arm_ex 등)은 **진짜 동작뿐 아니라 raw mocap의 고주파 노이즈(근육
미세떨림·마커 지터)까지 그대로 곱해서 키운다.** 두 가지 증상으로 나타났다:

1. **몸 관통** — `dance_arms`에서 팔 z가 -176도까지 나온 적 있음(리그 규약상 안전
   범위는 대략 [-130,130]). 원인은 decompose된 raw range 자체가 넓은데 거기에
   exaggeration까지 곱해서 한계를 뚫은 것. **해결: 최종 값에 하드 clamp**
   (`retarget.py`의 `clamp()` — 오른팔 z∈[-20,130], 왼팔 z∈[-130,20], 팔 x∈[-50,110],
   다리 x∈[-20,90], 척추/머리 x·z∈[-30,30] 근방).
2. **전반적 잔떨림("부들부들")** — 작은 노이즈도 exaggeration 배율만큼 커지면 매
   샘플마다 자잘하게 흔들리는 것처럼 보인다. **해결 두 단계**: (a) 평균중심화 *전에*
   `smooth()`(이동평균, window=5)로 고주파 성분을 죽인다. (b) 평균중심화 *후, 과장
   *전*에 `deadzone()`으로 원 진폭이 threshold(관절별 3~6도) 미만이면 통째로 0으로
   눕힌다 — "그 관절은 이 구간에서 안 움직인 것"으로 간주. **순서가 중요**: 데드존
   판정을 과장 후에 하면 이미 커져서 항상 통과해버려 무의미해진다.

또한 **소스 선택 자체의 함정**: `dance_arms`의 첫 시도(subject 49 "arms held high")는
이름 그대로 정적으로 든 자세라, 평균중심화하면 실제 신호가 거의 안 남고 노이즈만
남아 "떨기만 하고 안 움직이는" 결과가 나왔다. **"held"/"static"/"balance"가 이름에
들어간 trial은 피하고, 실제로 오가는 동작(스텝·스윙) 있는 소스를 고를 것** —
`cmu-catalog.md`의 체크리스트 참고.

## 망토(cape_cape) — 격렬한 애니에서 몸 관통함, scale 0으로 숨길 것

`cape_cape` 본(origin `[0,22.75,2]`, pc_chest 자식)은 원래 애니메이터가 없어서(회전
안 됨) 격렬한 척추/다리 동작 중에 몸을 그대로 뚫고 지나간다(유저 실사용 피드백,
2026-07-27). 고치는 법은 **회전을 맞추는 게 아니라 아예 숨기는 것** — `scale` 채널을
`(0.001,0.001,0.001)`로(완전 0은 일부 렌더러에서 0-나눗셈 이슈 우려로 피함) t=0과
t=length 두 키프레임만 주면 그 애니 재생 중엔 사실상 안 보이고, 다른 애니(감정표현·
제스처·breathe)로 넘어가면 cape 애니메이터가 없어서 자동으로 원래 크기(1,1,1)로
돌아온다 — 별도 복구 로직 불필요. 춤 9종 전부에 이렇게 적용됨. **새 이모트를 격렬하게
만들 때마다 이 스니펫을 잊지 말 것.**

## 루프 요구사항

`loop: "loop"` 애니는 **첫 키프레임과 마지막 키프레임 값이 정확히 같아야** 이음매 없이
반복된다(`retarget.py`의 `close_loop()`가 꼬리 15%를 크로스페이드로 처리). 회전값의
0°/360° 같은 "다른 숫자, 같은 각도"는 예외(정합성 검사에서 경고만 뜨고 실패 아님).

## 길이(window) — 너무 짧게 자르지 말 것

**2~3초로 자르면 반복이 금방 눈에 띄어 "싸구려" 느낌이 난다는 피드백을 실제로 받았다
(2026-07-27).** 기본값은 4초 이상(retarget.py `--window-sec` 기본 4.0), 소스 클립
길이가 허용하면 5초 이상도 좋다. 다만 소스 클립 자체 길이의 60~70%를 넘기지 말 것
(scan 단계에서 넘어가는 프레임이 없어야 함 — CLI가 알아서 clamp하지만 너무 타이트하게
잡으면 scan의 슬라이딩 폭이 줄어들어 최적 구간을 놓칠 수 있음).

## 배포 규약(공용 AGENTS.md와 동일)

애니메이션은 서버측 데이터라 리소스팩 재배포 불필요. dev는 파일 직접수정 후
`~/dev-mc.sh cmd "bm reload"`, prod는 scp 후 원격 RCON `bm reload` — 어느 쪽도
서버 재시작이나 jar 배포가 필요 없다. prod 배포 전엔 접속자 수 확인
(`ssh ... 'python3 ~/mcserver/scripts/rcon.py list'`) — 0명이면 바로 배포 가능,
있으면 원칙상 명시 요청 필요.
