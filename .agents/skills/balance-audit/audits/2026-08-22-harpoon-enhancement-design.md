# 작살 강화 설계 검토 — 2026-08-22

## 요약 (TL;DR)

- 종합 상태: 🔴 현재 작살은 강화 전부터 낚싯대를 크게 지배하므로, 낚싯대 강화표를 그대로 복사하면 안 된다.
- 기준 코호트 모델에서 작살/낚싯대 골드 비율은 적중률 0.50에서도 Lv.1 4.18배, Lv.70 5.20배다. 적중률 0.75에서는 Lv.1 4.57배, Lv.70 5.66배다.
- 현재 작살 55종은 이미 행운·속도·호흡·크리·공격의 5개 순수 계열과 17개 복합 계열로 설계되어 있다. 강화도 이 계열을 보존해야 한다.
- 권고 구조는 `수중/전투 주축 1개 + 낚시 보상 보조축 1개`다. 강화 전 스탯을 한 종류만 반복하거나, 낚싯대의 공통 수입 스탯을 통째로 복사하지 않는다.
- 이 문서는 설계 권고다. 런타임 수치와 강화 JSON은 사용자 승인 전까지 변경하지 않는다.

## 1. 권위 데이터와 드리프트

이번 검토는 `balance.md`의 숫자를 정답으로 삼지 않고, 라이브 Java·런타임 JSON·생성기를 기준으로 했다.

| 항목 | 현재 값 | 근거 |
|---|---:|---|
| 장비 카탈로그 | 226종 | `catalog.py`, parts.json |
| 낚싯대 / 작살 | 67 / 55종 | runtime parts.json |
| 작살 레시피 연결 | 51 / 55종 | recipes.json, 4종은 별도 경로 확인 필요 |
| 강화 테이블 | 81개 | runtime enhance.json |
| 현재 낚싯대에 없는 낡은 강화 프로필 | 16개 | enhance.json과 parts.json 대조 |
| 현재 낚싯대인데 강화 프로필이 없는 항목 | 2개 | `잠수부의 낚싯대`, `심해 잠수부의 낚싯대` |
| 스냅샷 경고 | 없음 | `2026-08-22.raw.json` |

`balance.md`는 강화 보상에 대해 “낚싯대별 개별 테이블”을 요구하지만, 현재 enhance.json의 신규 낚싯대 다수는 공통 `난이도:1, 행운:1` 패턴이다. 따라서 “현재 낚싯대의 고유 스탯을 참조한다”는 말은 이름 치환만으로 보장되지 않는다. 작살 설계에서는 `fish-tools/gen_spear_builds.py`의 빌드 선언을 1차 정체성으로 사용하고, 낚싯대 강화의 최대치·비용·실패·제물 구조만 공통 규칙으로 참조하는 것이 안전하다.

## 2. 현재 작살 경제의 전제

### 2.1 작살이 이미 강한 이유

현재 `cohort_sim.py` 기준 결과는 다음과 같다.

| 적중률 | Lv.1 작살/낚싯대 | Lv.60 작살/낚싯대 | Lv.70 작살/낚싯대 |
|---:|---:|---:|---:|
| 0.50 | 4.18배 | 4.69배 | 5.20배 |
| 0.75 | 4.57배 | 5.15배 | 5.66배 |
| 0.90 | 4.57배 | 5.15배 | 5.66배 |

주요 원인은 작살의 `약 514 캐치/h`, 품질 평균 85, 7초 캐치 쿨다운이며, 낚싯대는 미니게임 실패를 반영해 약 136~140 캐치/h·품질 평균 50이다. 따라서 강화의 수입 스탯을 낚싯대와 같은 크기로 더하면 작살은 숙련 보상이 아니라 구조적 우월 장비가 된다.

### 2.2 스탯 가치 관점

현재 스냅샷의 기준 원/h/단위는 판매보너스 1% = 222원, 더블 1% = 222원, 트리플 1% = 445원, 경험치 1% = 222원, 행운 1점 = 110원이다. 이 값은 낚시 기준이므로 작살에 그대로 곱하면 안 되지만, 작살의 처리량이 더 높다는 사실을 감안하면 공통 보상 강화는 낚싯대보다 작게 잡아야 한다.

## 3. 권고하는 강화 철학

### 3.1 공통 규칙

1. 최대 강화레벨·강화 비용·성공률·하락·보호권·별빛진주·체크포인트·동일 종류 제물은 낚싯대와 동일하게 유지한다.
2. 강화 프로필은 이름 유사도나 가격 근접도가 아니라 작살의 명시적인 빌드 계열로 선택한다.
3. 모든 프로필은 최소 2개 축을 갖는다. `주축 반복 + 3/5레벨마다 보조축` 구조로 단일 스탯 도배를 피한다.
4. `난이도`와 `내구보존`은 작살 강화에서 제외한다. 작살에는 낚싯대 미니게임과 내구 소모가 없기 때문이다.
5. `행운`은 전 프로필 공통으로 조금 넣을 수 있지만, 현재 작살의 처리량 우위를 더 키우지 않도록 낚싯대보다 낮은 빈도로 넣는다.
6. 공통 수입 스탯의 강화량은 대응 낚싯대 프로필의 35~50%를 1차 상한으로 둔다. 실측 1000캐치 이후에만 상향한다.

### 3.2 5개 순수 계열

| 작살 계열 | 강화 주축 | 보조축 | 낚싯대에서 참조할 원칙 | 의도 |
|---|---|---|---|---|
| 행운형 | 행운 또는 등급업 | 판매보너스 | 행운형의 주축+등급업, 히든은 행운 상단 | 희귀 등급/판매를 함께 노리는 탐색형 |
| 속도형 | 수영속도·돌진쿨감 | 경험치 | 성장형의 경험치/트리플 보조 구조 | 물고기를 찾고 다음 교전으로 넘어가는 회전형 |
| 호흡형 | 수중호흡 | 더블찬스 | 상인형의 보상 보조와 복합형의 안정성 | 오래 잠수하며 안정적으로 여러 마리 회수 |
| 크리형 | 크리확률·크리배율 | 크기 | 크리형의 확률·배율·크기 3축 | 한 번의 명중을 큰 보상으로 만드는 폭발형 |
| 공격형 | 공격력·공격속도 | 트리플찬스 | 성장형의 트리플 보조, 전투 게이트 우선 | 높은 HP 물고기를 제한시간 안에 뚫는 전투형 |

속도형·호흡형·공격형의 주축은 현재 낚싯대에 없는 작살 전용 스탯이다. 이 세 축을 진짜 강화 효과로 쓰려면 `getAttackPower`, `jabGapTicks`, `dashCooldownTicks`, `breathOf`가 강화 누적값을 읽도록 연결해야 한다. 연결하지 않고 JSON에만 넣으면 표시만 되고 실제 플레이에는 적용되지 않는다.

### 3.3 복합형

복합형은 두 계열을 각각 80% 정도로 적용하고, 한쪽을 주축으로 고정하지 않는다. 예를 들어 `겸업 작살`은 행운+크리, `사막탐사 작살`은 크리+공격, `왕립 순찰 작살`은 속도+호흡으로 구성한다. 복합형이 순수형보다 모든 면에서 강해지지 않도록 각 주축의 최고치 대신 두 축을 나눠 받는다.

## 5. 레벨별 보상 템플릿 권고

정확한 수치는 승인 후 별도 패치로 적용한다. 우선 구조는 다음과 같다.

| 구간 | 주축 | 보조축 | 마일스톤 |
|---|---|---|---|
| +1~+4 | 매 레벨 주축 1회 | +2, +4에 보조축 | 입문 체감. 공통 수입 스탯은 작게 |
| +5~+9 | 주축 유지 | +6, +8에 보조축 | +5에서 빌드 시그니처 1회 |
| +10~+14 | 주축 증가폭 확대 | +12, +14에 보조축 | +10에서 두 번째 시그니처 |
| +15 이상 | 주축 증가폭 확대 | 보조축은 완만하게 | +15 또는 +18/20에 최종 시그니처 |

작살은 이미 처리량·품질 우위가 있으므로, 공통 보상축의 최종 누적은 대응 낚싯대의 약 35~50%부터 시작한다. 반대로 속도·호흡·공격 같은 전용축은 직접 수입이 아니라 교전 체감과 접근성에 영향을 주므로, 실제 코드에서 적용한 뒤 `hit_rate`, `catch/h`, `escape_rate`를 따로 측정한다.

## 6. 구현 전 필수 정합성

1. `EnhanceManager.enhancementProfile()`의 가격·레벨 근접 fallback을 제거하고, 55종 명시 매핑 또는 `작살` 전용 프로필을 둔다.
2. `EnhanceLoader`의 테이블 이름 충돌을 피하기 위해 작살 프로필을 `작살|이름` 네임스페이스로 저장하거나, 타입을 포함한 JSON 구조로 확장한다.
3. `getAttackPower`, `jabGapTicks`, `dashCooldownTicks`, `breathOf`가 작살 강화 누적값을 읽도록 연결한다. 그렇지 않으면 전용축은 로어에만 보이는 가짜 스탯이 된다.
4. 강화 GUI·프로필·스탯 GUI에 전용축의 실제 단위와 적용 위치를 표시한다.
5. 적용 전후에 적중률 0.50/0.75/0.90과 실제 1000캐치 표본을 모두 비교한다. 기준 작살/낚싯대 비율이 계속 1.5배를 넘으면 공통 수입축을 올리지 않는다.
6. `balance.md`의 +20 표기, `gen_rod_builds.py`의 `ENH_MAX`(E1/D8/C10/B13/A15/S18), runtime enhance.json의 프로필을 하나의 권위 체계로 정리해야 한다. 지금은 이 셋이 드리프트한다.
