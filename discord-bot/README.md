# 바르칸 디스코드 봇

두 가지를 한다.

1. `/인증` — 게임 `/디스코드`로 받은 코드로 마크 계정과 디스코드 계정을 연결하고 인증 역할 + 에디션 표시 역할(`자바`/`베드락`)을 준다.
2. 길드 전용 채널·역할 — 게임에서 길드가 생기면 디스코드에 전용 텍스트/음성 채널과 역할을 만들고, 해체되면 대화를 백업한 뒤 지운다.

배포 위치는 오라클 `/srv/barkan-discord-bot`, systemd 유닛은 `barkan-discord-bot`.

## 에디션 표시 역할 (`자바` / `베드락`)

인증이 끝나면 연결된 마크 계정이 어느 에디션인지 보여 주는 역할을 하나 준다. **권한은 하나도 없는 순수 표시용**이고, 반대쪽 역할을 들고 있으면 회수해서 항상 한 개만 남긴다.

**판정은 디스코드 접속 기기(모바일/데스크톱)가 아니라 «연결된 마크 계정»으로 한다.** Floodgate 는 베드락 유저에게 `new UUID(0, xuid)` 를 주므로 UUID 상위 64비트가 전부 0이다(prod 실측 `00000000-0000-0000-0009-01f758e05895`). 서버가 이미 아는 사실이라 100% 맞다. 기기로 판정하면 이렇게 어긋난다.

| | 기기 판정 (PRESENCE) | 계정 판정 (지금 방식) |
|---|---|---|
| PC 로 자바 하면서 폰으로 인증 | **베드락으로 오판** | 자바 |
| 필요한 특권 인텐트 | `PRESENCE INTENT` 추가 | 없음 |
| 온라인 상태가 오프라인·투명 | **판정 불가** | 무관 |

기기 자체를 표시하고 싶어지면 그건 «에디션» 과 다른 사실이므로 별도 역할로 둘 것.

역할은 봇이 **없으면 만든다**(같은 이름이 이미 있으면 그걸 재사용). 이름·색을 바꾸려면 환경변수로 덮거나 디스코드에서 직접 고치면 된다 — 봇은 id 로 기억하고, id 가 사라지면 이름으로 다시 찾는다.

이 기능이 생기기 전에 인증한 사람과 디스코드를 나갔다 들어와 역할이 날아간 사람은 **30분 주기 백필**이 채운다(`/internal/discord/links`). vip-billing 이 아직 그 엔드포인트를 모르는 구버전이면 백필만 건너뛰고 인증 시점 지급은 그대로 돈다 — 봇을 먼저 배포해도 안전하고, vip-billing 이 올라오면 봇 재시작 없이 이어진다.

★**「인증 코드를 발급하지 못했습니다」 (베드락) 는 2026-09-05 prod 핫픽스로 해결됐다 — 단, 그 수정은 레포에 없었다.** vip-billing 의 `validUuid`/`minecraftName` 이 RFC UUID 버전·변종 니블과 `[A-Za-z0-9_]{3,16}` 만 통과시켜 Floodgate UUID(`0000...`)와 접두사 붙은 이름(`.taewon1507`)이 `/internal/link-codes` 에서 400 으로 튕기던 문제로, 운영자가 `/srv/vip-billing/server.mjs` 를 직접 고쳤다. **레포에는 옛 규칙이 그대로 남아 있어서 다음 vip-billing 배포가 이 핫픽스를 조용히 되돌릴 참이었다.** 그래서 그 규칙을 `vip-billing/player-identity.mjs` 로 되받아 오고 실측값 회귀 테스트를 붙였다.

★**vip-billing 은 prod 가 레포보다 뒤처져 있다** (토스 설정 잔존·멤버십 가격 개편·댓글 수정 기능 미배포 — 2026-09-07 기준 172줄 차이). 레포의 `server.mjs` 를 통째로 올리면 그 미배포 변경이 한꺼번에 딸려 나간다. 이 문서의 백필 엔드포인트도 그래서 **전체 배포가 아니라 해당 블록만** prod 파일에 넣었다.

## 길드 연동이 도는 방식

```
BlockShip(GuildDiscordBridge)          vip-billing                  이 봇
  길드 명부 전체 스냅샷  ──POST──▶  직전 상태와 비교 → 작업 큐  ──폴링──▶  채널·역할 조작
       (save() 마다, 3초 디바운스)                                    (5초마다)
```

개별 이벤트가 아니라 **명부 전체 스냅샷**을 보낸다. 이벤트 방식은 한 번 유실되면 그 길드가 영원히 어긋난 채 남지만, 스냅샷은 다음 전송에서 저절로 복구된다. 게임 쪽 훅 지점은 `GuildManager.save()` 하나뿐이다 — 생성·해체·가입·탈퇴·직책 변경이 전부 여기를 지난다.

## 길드 개명

게임의 `/길드 개명 <새이름>`은 길드 ID 자체를 바꾼다. 연동에는 두 가지가 필요하다.

1. **행 인수인계** — 게임이 개명 직후 24시간 동안 스냅샷에 `renamedFrom` 을 함께 실어 보낸다.
   vip-billing 이 이 힌트를 보면 `guild_discord`·`guild_mirror`·`guild_member_mirror`·대기 중인
   `guild_discord_jobs` 의 `guild_id` 를 새 ID 로 옮긴다. **이게 없으면** 다음 스냅샷이 개명을
   "옛 길드 해산 + 새 길드 신설"로 읽어 `guild_delete` 가 큐에 들어가고, 채널이 대화째 지워진다.
   힌트는 10분 주기로 다시 오므로 백엔드가 잠깐 죽어 있어도 다음 전송에서 복구된다.
2. **이름 따라잡기** — 행만 옮기면 채널·역할 이름은 옛 이름 그대로다. `provisionGuild` 가
   지나갈 때 `[길드] <이름>` / 텍스트 / 음성 이름이 다르면 그때만 `setName` 한다. 개명 전용
   경로를 두지 않은 이유는 30분 reconcile 이 같은 함수를 지나기 때문이다 — 작업이 유실돼도
   다음 정기 점검에서 맞고, 관리자가 손으로 바꾼 이름도 되돌아온다.

`renamedFrom` 힌트에 24시간 만료를 둔 이유: 무기한 보내면 훗날 누군가 옛 이름으로 길드를
새로 만들었을 때 그 길드의 채널을 엉뚱하게 물려줄 여지가 생긴다.

## 디스코드 상한 (부스트로 안 올라간다)

| 항목 | 상한 |
|---|---|
| 채널 총합 (카테고리 포함) | 500 |
| 카테고리 | 50 |
| 역할 | 250 |

그래서 **길드마다 카테고리를 파지 않는다.** 그렇게 하면 50길드에서 막힌다. 대신 `길드 1`, `길드 2` … 공용 카테고리 풀을 두고 길드당 채널 2개(텍스트·음성)만 넣는다. 역할도 길드당 1개(`[길드] 이름`)만 쓰고, 직책 표시는 공용 역할 4종(`길드장`/`부길드장`/`간부`/`길드원`)을 돌려 쓴다. 이 구성의 상한은 약 245길드다.

## 권한 설계 — 아무 권한도 주지 않는다

길드 역할과 길드 채널에는 관리 권한을 **일절** 주지 않는다. 길드 채널은 "길드원에게만 보인다"가 전부이고 메시지·채널 관리는 서버 운영자만 한다.

채널당 오버라이트는 딱 2개다.

- `@everyone` → 보기 거부
- `[길드] 이름` → 보기·쓰기·음성 접속

디스코드 권한은 역할을 OR로 합치므로 "두 역할을 모두 가져야 성립"하는 AND 조건은 만들 수 없다. 공용 `길드장` 역할에 서버 단위 `채널 관리`를 주면 그건 모든 채널에 적용되고, 오버라이트 수정 권한까지 따라와서 남의 길드 채널을 열어볼 수 있다. 채널 오버라이트로 주는 형태는 `VIEW_CHANNEL` 묵시적 차단에 기대게 되는데, 문서상 `MANAGE_CHANNELS`는 그 목록에 없고 음성 채널은 `CONNECT`가 기준이라 막히지 않는다. 그래서 권한을 아예 안 주는 쪽으로 정리했다.

나중에 "길드장이 메시지는 지울 수 있으면 좋겠다"가 나오면, 그 길드 채널에 **유저 단위** 오버라이트를 얹으면 된다. 지금 붙이든 나중에 붙이든 비용이 같아서 미리 넣지 않았다.

## 최초 설정 (한 번만, 손으로)

1. **봇 권한** — 초대 링크 권한에 `Manage Channels`, `Manage Roles`, `Read Message History`를 포함해 재초대하거나, 서버 설정에서 봇 역할에 추가한다. 셋 다 없으면 각각 채널 생성 / 역할 부여 / 해체 백업이 실패한다.
2. **특권 인텐트** — 개발자 포털 → Bot → `SERVER MEMBERS INTENT`를 켠다. 없으면 역할 회수와 재입장 복구가 조용히 안 된다.
3. **역할 순서** — 봇 역할이 `[길드] *` 역할과 공용 직책 역할보다 위에 있어야 한다. 새로 만든 역할은 맨 아래에 생기므로 보통 저절로 만족한다.
4. **환경 변수** (`/etc/barkan-discord-bot.env`)

   | 변수 | 기본값 | 설명 |
   |---|---|---|
   | `GUILD_CATEGORY_PREFIX` | `길드` | 공용 카테고리 이름 접두어 |
   | `GUILD_ARCHIVE_DIR` | `/srv/barkan-discord-bot/archive` | 해체 로그 JSONL 위치. systemd `ReadWritePaths` 안이어야 한다 |
   | `DISCORD_JAVA_ROLE_NAME` | `자바` | 에디션 표시 역할 이름 |
   | `DISCORD_BEDROCK_ROLE_NAME` | `베드락` | 〃 |
   | `DISCORD_JAVA_ROLE_ID` / `DISCORD_BEDROCK_ROLE_ID` | (없음) | 이미 만들어 둔 역할을 쓸 때만. 비우면 이름으로 찾거나 새로 만든다 |

공용 역할 4종과 에디션 역할 2종, 카테고리는 봇이 없으면 알아서 만든다. 같은 이름의 역할이 이미 있으면 그걸 재사용한다.

## 해체 로그

길드가 해체되면 텍스트 채널 전문을 `GUILD_ARCHIVE_DIR`에 JSONL로 남기고 채널·역할을 지운다.

```
<길드이름>-<ISO시각>.jsonl
{"type":"meta","guildId":"기모띠","channelId":"...","messages":1234,"truncated":false,"archivedAt":"..."}
{"type":"message","id":"...","at":"...","authorId":"...","authorTag":"...","content":"...","attachments":[],"embeds":0}
```

첨부파일은 URL만 남는다(파일 자체는 디스코드 CDN에 있고 채널이 지워지면 언젠가 사라진다). 메시지 20만 개를 넘으면 자르고 `truncated: true`로 표시한다.

**이 디렉터리는 백업 대상에 들어 있지 않다.** 오프사이트 백업은 BlockShip 폴더와 월드만 뜬다. 보존이 중요해지면 `offsite-backup.sh`에 추가할 것.

## 안전장치

- **대량 삭제 방어** — 스냅샷이 한 번에 3개 이상이면서 전체의 절반을 넘게 지우려 하면 백엔드가 409로 거부하고 경고를 남긴다. 게임 쪽에서 `guilds.json`을 못 읽은 상태로 빈 스냅샷을 보내는 사고를 막는다. 진짜 대량 해체라면 `{"guilds":[...],"force":true}`로 보내야 통과한다.
- **작업 순서** — 큐는 항상 id 순으로 처리한다. 순서가 섞이면 삭제 뒤에 생성이 돌아 지운 채널이 되살아난다.
- **해체된 길드의 잔여 작업** — 큐에서 꺼낼 때 명부에 없는 길드의 생성/멤버 작업은 `guild_gone`으로 종료한다.
- **실패 백오프** — 30초 × 시도횟수(최대 3분)로 미뤘다가 재시도, 10회 넘으면 포기하고 다음 전체 동기화에 맡긴다.
- **정기 점검** — 30분마다 기대 상태와 대조해 사라진 채널·역할을 다시 만든다.

## 테스트

```bash
npm install
npm test
```

실제 디스코드를 때리지 않는 부분(역할 계획 계산, 카테고리 배치, 이름 정규화, 에디션 판정·부여)만 검증한다. 베드락 UUID·이름 검증은 `vip-billing` 쪽 `player-identity.test.mjs` 에 있다.
